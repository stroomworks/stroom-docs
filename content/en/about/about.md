Stroom is a data processing, storage and analysis platform.
It receives large volumes of machine data, such as system and audit logs, stores it in its original form, normalises it into a common structure, and lets you search, visualise and alert on the result.
It scales by adding more nodes to a cluster.

Most of its users are doing security monitoring, audit or investigation, where questions are often asked long after the data arrived.


## What Stroom does

* **Data receipt.**
  Data is sent to Stroom over HTTP(S) on a named [feed]({{< relref "/docs/concepts/feed.md" >}}) and stored exactly as it was sent.
  The raw data is always kept, so it can be reprocessed at any time.
  See [Data receipt]({{< relref "/docs/concepts/data-receipt.md" >}}).
* **Stroom Proxy.**
  A separate application that receives data, aggregates it and forwards it to Stroom or to other destinations.
  It can sit at the edge of a network or close to the systems sending data.
  See [Installing a proxy]({{< relref "/docs/operate/install/a-proxy.md" >}}).
* **Pipelines.**
  Configurable [processing pipelines]({{< relref "/docs/concepts/pipelines.md" >}}) parse, translate, filter and write data.
  _Data Splitter_ parses text formats (delimited, fixed width or multi-line records) into XML, and XSLT translates that XML into a common schema, typically the [_event-logging_ XML Schema](https://github.com/gchq/event-logging-schema).
  Pipelines can be stepped through record by record in the user interface to develop and debug translations.
  See [Translation]({{< relref "/docs/concepts/translation.md" >}}).
* **Reference data.**
  Events can be enriched during translation by looking up values, such as user or host details, in [reference data]({{< relref "/docs/concepts/pipeline-reference-data.md" >}}) that is valid for a given point in time.
* **Indexing and search.**
  Processed events can be indexed in Stroom's own [Lucene indexes]({{< relref "/docs/concepts/lucene-index.md" >}}), which are sharded across the cluster, or sent to [Elasticsearch]({{< relref "/docs/guides/indexing/elasticsearch.md" >}}).
* **Dashboards and queries.**
  [Dashboards]({{< relref "/docs/concepts/dashboards.md" >}}) query indexes, statistics and other data sources and show the results in tables and [visualisations]({{< relref "/docs/concepts/visualisations.md" >}}).
  [StroomQL]({{< relref "/docs/concepts/query-language.md" >}}) is a text query language for the same data sources.
* **Analytic rules.**
  An [analytic rule]({{< relref "/docs/guides/detection/analytic-rules.md" >}}) is a StroomQL query that Stroom keeps running.
  Each matching row is a detection, which is sent to a feed or by email.
* **Annotations.**
  Search results can be [annotated]({{< relref "/docs/guides/detection/annotations.md" >}}) with a status, an assignee and comments, so that analysts can record and track their investigation of events.
* **Plan B.**
  [Plan B]({{< relref "/docs/concepts/planb.md" >}}) is a state store built on LMDB.
  It holds state, temporal state, ranged state, sessions, metrics and histograms, which pipelines can write to and look up from, and which can be queried.
* **Statistics.**
  Counts or values can be recorded over time, answering questions such as "how many events has this host sent in the last hour?".
* **Content packs and Git.**
  Stroom content (pipelines, translations, schemas, dashboards and so on) can be held in Git repositories and pulled into or pushed from Stroom.
  Ready-made content packs are installed from a content store.
  See [Content management]({{< relref "/docs/guides/content-management.md" >}}).
* **AI features.**
  Stroom can call an AI model that has been configured in Stroom.
  This is used by the _Ask Stroom AI_ chat panel, by the `ask-ai()` XSLT function and the `askAi()` dashboard and StroomQL function, and to add summaries to reports.
  See the [release notes]({{< relref "/releases/_index.md" >}}) for 7.13 and 7.14.


## Benefits

System event data comes from many kinds of technology, so it is highly heterogeneous, with many different formats in use.
As technologies are introduced, new event types and log formats must be understood and processed correctly.

Stroom is designed to manage this, and scales to billions of events a day, enough to ingest and process the system events generated by the IT of a large organisation.

The person who introduces a new log format is probably best placed to describe it.
Stroom gives these experts the tools to normalise the data themselves, so that the work of supporting new formats is shared.

### Processing overview

Stroom has a configurable pipeline based processor that allows multiple processing pathways for received data.
Raw data is processed to "cook" it into a normalised form, so data originating from hundreds of different log formats can then be processed in the same way.
The common form for cooked data is usually the [_event-logging_ XML Schema](https://github.com/gchq/event-logging-schema).
Cooked data can be processed further to index, aggregate or analyse it, or to send it to other systems.

{{<image "about/processing_overview.puml.svg" >}}Processing Overview Diagram{{</image>}}

The main processing stages are:


#### Parsing

Data arrives in many forms, such as CSV, JSON or XML, so it is first parsed into a simple XML form that mirrors the raw data.
_Data Splitter_ parses text based logs, whether they are delimited, fixed width, or have complex multi-line records.
XML and JSON data are handled by their own parsers.


#### Translation

Translation can involve a number of steps.
The first is to translate the simple XML into the common _event-logging_ form, for example turning Windows event logs and Linux auditd logs into the same structure.
For bespoke log formats this translation can be written by the owners of the system sending the log.
Translation usually also decorates each event with reference data lookups, for example looking up a user ID in reference data from a human resources system, or a hostname to find the location of a device.


#### Writers, filters and appenders

Once events are in a common, decorated form they can be transformed into other forms for indexing, statistics, state stores, or for sending on to other systems.
Typically the cooked events are stored and also transformed into a form suitable for indexing.


#### Reprocessing

All processed data in Stroom can be reprocessed at any time, for example after a translation has been improved.


## Architecture

Stroom is a Java web application.
The current version is built on Java 25 and runs on _Dropwizard_ with embedded _Jetty_.
The user interface is written with _GWT_ and talks to the server through REST APIs, which are also available to other clients.
_Guice_ is used for dependency injection and _jOOQ_ for database access.

Stroom stores its configuration and metadata in _MySQL_.
Received and processed data is held in a compressed stream store on disk.
Reference data, search results and Plan B stores use _LMDB_.

Stroom runs as one or more [nodes in a cluster]({{< relref "/docs/concepts/nodes-and-clusters.md" >}}) that share a database.
Processing tasks and index shards are spread across the nodes.
Stroom authenticates users with OpenID Connect, using either its own built-in identity provider or an external one.

Related projects include:

* [Stroom Proxy](https://github.com/gchq/stroom) - Receives and forwards data to Stroom; it is built from the same repository as Stroom.

* [event-logging-schema](https://github.com/gchq/event-logging-schema) - An XML Schema for describing auditable events.
* [event-logging](https://github.com/gchq/event-logging) - A Java (JAXB) library for the _event-logging_ XML Schema.

* [stroom-resources](https://github.com/gchq/stroom-resources) - Docker configuration and released Docker stacks.


## History

Stroom was developed by GCHQ for collecting, processing and analysing large volumes of log data.
It was released as open source under the Apache 2.0 licence in 2016, and Stroom v5 was the first open source release.
It continues to be developed in the open on [GitHub](https://github.com/gchq/stroom).

For what changed in each version, see the [release notes]({{< relref "/releases/_index.md" >}}).

### Stroom content

Much of the power of Stroom comes from the content developed within it, such as XSLT translations, Data Splitter definitions, dashboards, visualisations and pipelines.
This content can be shared between Stroom installations, either through Git repositories or as exported zip files.

Generic Stroom content is available from [stroom-content](https://github.com/gchq/stroom-content), and visualisations from [stroom-visualisations-dev](https://github.com/gchq/stroom-visualisations-dev).
